## A. Facet 独立记录身份的挂载与归属（对应 §15 G1-b，清单 `G1-FACET-01`）

**这是 Q45 合法跨 Capability Facet 写入正例的前提**：没有「挂载登记」这一机制事实，机制面就
无法在放行合法 Facet 与拦下伪造行之间做出任何区分——不是意愿问题，是**没有可判的事实**。

### A.1 问题事实（全部实测，出处逐条）

1. `NamespaceWriter.write()` **只判 `ns`、从不判 `oid`**（`kernel.ts:614`；席位 `RE-REVIEW-G1-A.md` §③ N2，P1）。
   五条落点全部实测（`READINESS.md:119`）：种幽灵 oid；伪造修订级 required 硬引用（`:934` 修订判据不带 ns）；
   幽灵 `from` 使 `linkRef` 归属判定整段跳过（`:807`）；`readAsOf` 不按 ns 过滤 ⇒ 伪造行**作为他人对象的
   状态行被端出**（附 payload）；`write()` 顺手写 `ledger`+`journal` ⇒ 注入他人事件流且通过投影缺口检测。
2. 两个无歧义子集已修（包 1：幽灵 oid `NOT_FOUND_IN_SPACE`、修订判据 join `object_directory` 按归属 ns 归因，
   `CONTRACTS.md` §16.1 ①②）；读侧归属已修（包 6：`readAsOf` 每行过**同一个** `routeNs` 判据，
   `CONTRACTS.md` §16.3「D-24 读侧」段）。**写侧完整修法停在同一个事实上**：
3. 「合法 Facet 挂载」与「A-2 伪造行」在 `write()` 入口是**同一行形态**（ns=自己、oid=他人核心对象、
   任意 revision），机制层没有「扩展挂载登记」可区分（`READINESS.md:119`、`CONTRACTS.md` §16.1「已知缺口」段、
   PLAN §15 G1-b）。
4. 一刀切「oid owner == 写入 Capability」**已被门禁实测否证**，不是风格偏好：`attacks/review/g1a-regression.test.ts`
   有一条 **Q45 正例护栏**——「Facet 挂扩展记录到他人核心对象必须成功」，已入 `attacks/BASELINE.json` 的
   `passes` 集合（`READINESS.md:119`）；`g0-gate.mjs` 对审查方流要求通过集合与基线**逐等**（G-2 修法，
   `READINESS.md:117`）⇒ 打死正例的修法当场让门禁红，且这是**每次门禁运行都在重复的否证**。
   `CONTRACTS.md` §16.1 已把它写成契约：「**不采用**『oid 主能力 == 写入能力』的一刀切（那会打断 Q45 正例，
   护栏测试持续阻止该回头路）」。
5. 已裁定边界（不是待议项，是 A 节的约束条件）：#44 §6.2（`V3_CODE_ARCHITECTURE_DRAFT.md:200-208`，Q45）——
   Facet 是**面向已存在对象的独立领域扩展记录**，不是第六类对象（§5.2 `:178`「正式领域对象种类不因 Facet 增加」）；
   核心身份字段只有主 Capability 写，Facet 只有**自己的数据、记录标识、版本与生命周期权威**；挂载可按
   `ObjectRef` 导航，但**正式科研主张/检查/历史引用必须精确绑定 `RevisionRef`**、不得隐式 latest；
   **禁止平行复制**（RD-15/RD-37/XC-28）；有独立科研指称者须走 Domain Admission 成正式对象，
   **Facet 记录 ID 不得冒充科研对象 ID**（RF-05/06）；另 `:325`：Facet 有自己的 Schema/记录版本，
   不能覆盖对象核心 Revision。PoC 已实证面：`RECONCILIATION.md` §3 第 8a 行（每 Facet 能力独立拥有
   自己的记录与版本；`NAMESPACE_ESCAPE` 越权拒绝，P2）。

### A.2 为什么不能一刀切成「oid owner == 写入 Capability」（被点名的否证推理）

1. **语义上**：Facet 的既定用途就是「以他人核心对象为键写自己的扩展记录」——行形态 ns=扩展者自己、
   oid=被扩展对象。判「oid 的 owner 必须等于写入者」等于宣布 Q45 Facet 无法写扩展记录，
   与 #44 §6.2 前半句（Facet 有自己数据权威**且挂接既有对象**）正面矛盾。
2. **机验上**：正例护栏已在基线 `passes`（A.1 第 4 条）——该修法不是「我们认为不好」，是**回归门禁持续判红**。
3. **根因上**：D-24 的病不是「写他人 oid 被允许」，是机制**缺少可判的区分事实**。一刀切把「挂载」与
   「伪造」合并处理，五条落点只是被整体禁写压住——扩展能力也一起死。正确方向是**让区分事实进机制**
   （挂载登记），伪造行因无登记照旧全拦，正例照旧通过。
4. 顺带否证另一个变体：「允许写但事后审计」同样不成立——伪造行的落点之一是 `readAsOf` 以他人之名端出
   payload（A.1 第 1 条），**读面已经消费了伪造事实**，事后审计救不回错误归因。

### A.3 备选方案

| 案 | 形状 | 要点 |
| --- | --- | --- |
| **A1 挂载登记表** | 新机制注册表 `facet_mount`：挂载方 Capability、扩展记录 kind/ns、挂载目标 oid、绑定的核心修订（或明示的跟随政策）、生命周期状态。`write()` 对「oid 归属 ≠ 本能力」的行**只放行持有效挂载登记者**；登记的写入本身走机制独占入口（复用 §16.2 权威入口的判据排布：激活核对先行、零残留） | 行形态判据 ⇒ 登记判据；不新增表之外的读面语义 |
| **A2 物理分离** | 扩展记录不落「以核心 oid 为主语的 `domain_state` 行」：自有记录身份（record id ≠ 核心 oid），挂载目标降为**行内字段**；核心读面按构造永不见扩展行 | 挂载不再是「oid 主语行」问题；record id 独立性直接满足 RF-05/06 |
| **A3 声明事件形** | 不建新表：挂载 = 一条权威事件（§16.2 入口族），`write()` 判「该对象事件流中最新挂载声明」；撤销 = 同族 WITHDRAW 事件 | 零新表；代价见 A.4 |

### A.4 各自的不变量与代价

- **A1**：*不变量*——核心身份/kind/核心修订仍只有主 Capability 写（Q45 边界一字不动）；「他人 oid 上的行」
  从「无判据放行」变为「有登记才放行」；Kernel 零科研语义（挂载词表 = 挂载方/目标/修订，全是机制词）。
  *代价*——一张新表 + 打开期判据；挂载生命周期语义（Facet 卸载后登记状态与历史可见性）；多一个机制写面
  = 多一条攻击面，须与守卫同批配护栏测试（D-27/D-28 的教训：新写面若无触发器/预留同批，就是下一个洞）；
  挂载信息是否上插件读面属 E-01 同族信息面裁定，默认**不上**（只上「有无有效挂载」的机制内部判定）。
- **A2**：*不变量*——`domain_state` 归属判据收敛为「所有行都是属主行」，包 6 的读侧剔除逻辑可整体退役；
  扩展记录身份天然独立（record id ≠ 核心 oid）。*代价*——DDL/触发器/迁移（G2 真实 DDL 前禁动，G1 只定形状）；
  存量 PoC 世界的挂载行需要迁移语义（D-6 同款回填器债务家族）；XC-28 单一正源判据必须扩到「扩展行 vs
  核心字段/边」的重复形态（现在只查 payload 字段与已注册边并存，`RECONCILIATION.md` §3 8b 行）。
- **A3**：*不变量*——复用 §16.2 的机制独占与见证形状，无新存储原语。*代价*——挂载判定要按对象重建事件流
  （读放大）；**事件名权威必须先有 C 节的预留规则**（挂载/撤销事件名本身就是新的机制域名字）；
  历史库从未有挂载事件 ⇒ 存量挂载无从判（回填债）；撤销语义依赖同族新名，链条最长。

### A.6 冻结前必须回答的开放问题

1. 挂载登记的**绑定粒度**：登记绑 oid 还是绑 `RevisionRef`？#44 §6.2 只裁「正式科研主张必须精确绑修订」，

2. 核心修订**演进/作废**时挂载声明是否失效重验（修订不可变 ⇒ 挂载快照恒真，但「被扩展对象已无该修订」

3. Facet **卸载/换包**（Q44 移交通道）时挂载登记的状态迁移；历史记录可见性（归属账本不随停用消失，§16.2 先例）。
4. 挂载信息的**读面语义**：拒绝与「无挂载」是否同形（E-01 家族的 refuse vs withhold 裁定顺位）。
5. **XC-28 单一正源**判据归属：扩展行不得成为核心关系的第二真源——判据由领域出、机制执行还是机制自判？

6. 挂载登记表自身属**历史面**：B 节的 ns 重定位必须覆盖它（否则换 ns 后挂载指向幽灵）。

### A.8 第六轮裁定补充约束（2026-10-31，本轮新增；只补不推翻，与 A.1–A.7 全文并存）

裁定立场：「**支持 A1 的显式挂载机制 + A2 的独立记录身份约束，而不是只冻结 A1、
等写 DDL 时再讨论记录究竟是谁**」——A.5 的「A2 记为 G2 物理形态方向」据此收窄：
A2 里被点名的是**记录身份约束**，它不等 DDL，本轮就进 G1 冻结范围。

1. **记录身份区分进 G1 冻结范围**：`FacetRecordID`（扩展记录自身标识）与 `FacetRevision`
   （扩展记录自身修订）同被挂接对象的 `ObjectID` / `RevisionRef` 是**两套身份**；
   核心对象的修订归主 Capability，扩展记录及其修订归 Facet Capability；
   **挂载登记不得把目标对象 ID 充当 Facet 自身版本身份**（RF-05/06 的机制化落点，
   也是 A.3-A2「record id 独立性」被冻结的半句）。
2. **绑定粒度四条**（裁定文本，覆盖 A.6-1 的原开放点）：
   ① 普通挂载指向稳定 `ObjectRef`，并记录**记录建立时的目标修订**（快照事实，非跟随承诺）；
   ② **承载正式科研声明 / 历史证据 / 检查结果的内容必须精确绑定 `RevisionRef`**
   （RD-05 在挂载面的直落点，不许隐式 latest）；
   ③ 核心对象的新修订**不自动改写**既有 Facet 记录的历史解释——是否触发重验由领域规则
   决定（机制面只提供绑定事实，不做跨域重解释，与 D-20「不得事后重解释历史」同族）；
   ④ **卸载 / 解除挂载 / 所有权移交是三种不同操作**：卸载 = 实现退出（历史保留，Q44）；
   解除挂载 = 挂载登记状态迁移（历史记录仍可读）；移交 = 权威变更（受控移交通道）。
   **不得以卸载替代撤销或删除历史**（H 面纪律在挂载面的延伸）。
3. A.6-1 状态更新：绑定粒度已由第六轮裁定（上文四条），不再作为开放问题悬置；

## B. 物理命名空间可迁移 vs 逻辑身份不可变（对应 Q44 / D-31 历史面，清单 `G1-NS-01`）

### B.1 问题事实（全部实测，出处逐条）

1. **已裁的是逻辑面**（Q44）：`ObjectID`/`CapabilityID`/`PluginID` 分离，ObjectID 生命周期不跟随源码重构，
   跨包拆分/合并不改变对象 ID；所有权转移要受控、可审计、原子切换；Capability 实现可迁包
   （`V3_CODE_ARCHITECTURE_DRAFT.md` §6.1 `:196-198`、§5.2 `:174`、`:120`；§15 表 `:412`「包可拆、单 Space
   唯一写者、显式移交」；`ASSESSMENT.md:196` F-27「显式迁移 + 受控移交，两步走」）。
2. **物理 ns 的现状 = 无通道可改**：`dir.ns` 是 Directory 创建时固定登记的出生事实（F-03，
   `RECONCILIATION.md:108`——换实现不迁 ns 曾静默返回空，修法为固定登记 + 读写同源 `routeNs` 漂移即
   `SCHEMA_INCOMPATIBLE`）；D-28 裁定「owner 一经登记不可变更」后 `object_directory` 身份行不可改不可删
   （`directory_no_update`/`directory_no_delete`/`directory_birth_audited`，`CONTRACTS.md` §16.2 包 5）
   ⇒ **`dir.ns` 无任何正当写通道**。
3. **D-31 事故**：包 5 的「owner 不可变」与 `transferRoute` 携 ns 并存过一次，产物是「一次完全合法、
   全走机制通道（`capability-admin`）的操作 = 永久毒化全库双时间读面」（`READINESS.md:206`）。包 6 止血
   取「移交不携 ns」：`reassignRouteInternal` 删除 ns 参数，清单 ns 降为校验输入，漂移入口即拒
   `TRANSFER_NS_DRIFT`，零半成品（`CONTRACTS.md` §16.3「D-31」段）。契约原文自己写下：**「ns 迁移另立
   显式迁移通道（机制没有，也不拿移交面凑数）」**。
4. **历史面敞开**（F-G6A-4，`READINESS.md:245`；`RE-REVIEW-G6-A.md` §① 3a 行）：v6 漂移库（按包 5 **合法通道**
   造的 `dir.ns ≠ route.ns`）重开撞 `SCHEMA_INCOMPATIBLE` 是**被版本墙顺住，不是被检出**（版本对齐后即零声纳）；

### B.2 备选方案

| 案 | 形状 | 判据 |
| --- | --- | --- |

### B.3 各自的不变量与代价

- **B0**：*不变量*——零新机制；身份与物理完全绑定。*代价（实测）*——漂移库**无检出、无救济**（B.1-4）；
  Q44 的实现迁移语义在存储面半死：新实现只能**继承旧物理 ns 名**，「拆包/迁移」在存储层退化为名称考古；
  版本墙「顺住 ≠ 检出」意味着**下一次版本对齐时洞自动开**——这不是边界，是延迟。
- **B1**：*不变量*——逻辑身份面（`ObjectID`/kind/space/owner）一字不动；**D-28 裁定不被重开**（身份行仍
  不可改不可删，`directory_no_update` 原样保留）；出生 ns 作为历史事实永久可审计（重定位链 append-only）；
  检出与救济同源于同一条见证——**漂移的唯一合法解释就是一条重定位账**，伪造漂移等价于伪造账（与 F-G6A-2
  的「伪证借 H 不可删获得不可篡改性」同族，守卫必须核信封，见开放问题 1）。
  *代价*——一条新机制写通道（预留/守卫/变异护栏必须同批，D-27 教训）；读归属函数加一维；打开期全表比对
  成本（一次性）；跨进程陈旧窗口（D-25 家族，见开放问题 4）。
- **B2**：*不变量*——通道更短（一条 UPDATE + 见证）。*代价*——与 D-28 裁定正面冲突；「留可变列而无正当写者
  正是本洞根因」是包 5 裁定 `owner` 时的原话（`READINESS.md:157`），B2 把同一根因重新引进 `ns` 列；
  出生 ns 信息被抹掉（历史取证丢字段）；UPDATE 触发器守卫面加宽——守卫词法判据的已知残余（D-30 登记）
  直接成为攻击面。**B2 的代价 = 重开一条已裁定面，G1 无权顺带重开 D-28。**

### B.4 建议与理由

**选 B1**，并把「物理 ns 不是科研身份」写成契约明句：*不可迁移的是逻辑身份（ObjectID/kind/space/owner
Capability/逻辑 Capability 所有权与唯一写者），可迁移的是物理存储命名空间——迁移只经显式、原子、带机制
见证的重定位通道，且出生 ns 永久可审计*。理由：(i) 不与任何已裁定语义相撞（Q44 被**补全**而非改写，
D-28 一字不动）；(ii) F-G6A-4 的「无检出 + 无救济 + 无通道」三无一次补齐，且检出与救济同源；
(iii) 互斥的真正化解点：G6-A 说「迁移通道与 dir.ns 冻结互斥」的前提是**迁移必须改写身份行**——B1 把
迁移改为「route 改写 + append-only 账」，互斥消失；(iv) 重定位事件名天然是 C 节命名空间规则的第一个
新客户，顺序上倒逼 C1 先行（见 C 节建议）。

### B.7 第六轮裁定补充约束（2026-10-31，本轮新增；只补不推翻）

裁定立场：「**B1 可作首选，但不能直接冻结当前文本**」——B 节升为冻结文本的前提是下列
**五项技术不变量**逐条写入（缺任何一项都不许冻结 B 节）：

1. **迁移前数据校验与目标位置准备**：重定位开始前必须校验待迁数据完整可解析、目标物理
   ns 已建立且就绪（校验清单属 #47 决策面，B.6 该行不因此关闭）；校验不过 ⇒ 零切换。
2. **数据复制/重定位的唯一权威 + 历史修订身份不变性**：迁移动作只有一个机制通道可执行
   （B1 的 `relocateNamespace`，别处一律不可表达）；复制/重定位**不改写任何修订身份**——
   行内容、`RevisionRef`、seq 与 ledger 引用逐字节不变，变的只有物理归属路由与账。
3. **活跃路由切换的原子性**：`capability_route.ns` 改写与重定位账追加在同一事务提交
   （不存在「路由已切、账未落」或「账已落、路由未切」的可观察中间态）。
4. **失败/崩溃/重试/跨版本读取的恢复条件**：切换事务前崩溃 ⇒ 旧路由照常；事务中崩溃 ⇒
   SQLite 原子性 ⇒ 两态之一；重试幂等（同参数重放不产生第二笔账）；崩溃窗口内的跨版本
   读取按「出生 ns + 账」两源解析，读到哪个态都自洽可归因。恢复条件必须逐条写成判据，
   不许以「事务保证一切」一句带过（D-23/D-25 家族的教训：保证范围必须写明边界）。
5. **旧 ns 内容不得因复制被当成新的科研历史事件**：迁移读旧写新是**物理动作**，不产生
   ledger 事件、不改 seq、不进投影——科研史不因搬家多一页（与 C 节「新名不许洗历史」、
   A.8-2③「新修订不改历史解释」同族的第三面）。

**backfill（存量漂移入账）裁定写死**（覆盖 B.5-1 的方向，B.5-1 的授权细节开放点收窄为
「授权主体名单与证据形状」）：

- **默认禁止自动补造「当时合法迁移」的证据**——没有任何自动机制、打开期扫描或迁移器
  可以为先例漂移生成重定位账。
- 唯一合法入账 = **具备运维授权的主体**在**验证原始库/备份/来源**之后做的**一次显式修复**；
  账必须**永久保留「事后修复」与「当时发生的合法迁移」之别**（分明的来源字段，事后不得抹）。
- **无法证明来源时隔离并报告，不得用一条新 relocation 事件把未知漂移洗成合法历史**——
  这条是本节防线的最后一句：重定位账的签发者若能在无来源时落账，B1 的「检出-救济同源」
  就退化为「伪造救济同源」（F-G6A-2 伪证族的镜像，必须在此切断）。

## C. 机制事件命名空间与授权签发（对应 F-G6A-6 / F-G6A-2 / G6-A 三句裁决位①，清单 `G1-EVT-01`）

### C.1 问题事实（全部实测，出处逐条）

1. **当前默认策略 = deny-by-exception**：事件名预留是**白名单枚举制**——包 6 把五个机制审计名
   （`capability-enabled/-disabled/-transferred/object-registered/check-report-recorded`）加正式事件名送进
   预留通道（`isReservedEventType` = 正式名 ∪ 机制审计名，`READINESS.md:196`、`CONTRACTS.md` §16.3 D-27 真修①）。
   名单**外**的名字照常可 mint：席位实证 `object-revised`（`kernel.ts:1231`，revise 自己在写）、
   `record-backfilled`（`migrateLegacyRecords`）与任意未来名（`capability-reloaded`、`capability-migrated-v9`……）
   经通用台账通道写入成功（G6B-D27-3，`RE-REVIEW-G6-A.md` §① 1c 行）。席位原话：「今天没洞只因为
   没有任何触发器/判据依赖这两个名——**『没洞』是巧合，不是设计**」。
2. **枚举式判据的同类失败已不是第一次**：方向判据③的「随附审计三元组名单」漏了「capability 主键
   出现/消失」这一维 ⇒ 停用复活·PK 改名链三步全程零启用审计（F-G6A-3，`READINESS.md:244`，清单
   `G1-ROUTE-01`）；`REQUIRED_TRIGGERS` 名单与 SCHEMA 同源 ⇒ 「删定义」形态对 digest 判据是设计外真空
   （G6-A §④ `:320-331`，清单 `G1-STORAGE-02`）。**名单制判据的系统性弱点是本节的真正对手**，不只是事件名。
3. **`authority_basis` 现状**：JSON 见证信封 `{axis, capability, authorized}`，机制独占写入
   （`appendAuthoritativeEvent` 入参无字段可填它，`CONTRACTS.md` §16.2 判据③；路由三写方包 6 起同信封盖章）。
   `ledger.actor` 由机制从已验证主体写下（「签发主体是机制事实，不是载荷字段」，§16.2）。
   **但信封里没有 `actor`**，而 `route_change_guarded` 守闸只核 `l.actor is not null` ⇒
   `actor=任意他人主体` 照过，只有 NULL 被挡（F-G6A-2，`READINESS.md:243`）：
   **「核的是『有一个 actor』，不是『这个 actor 有权』」**。席位给的修法：闸追加信封一致性
   `l.actor = json_extract(l.authority_basis,'$.actor')` + 机制侧信封增写 `actor`（取证同源）。
4. 轴值侧已有判据：`requiresAuthority` 轴名不得是机制自身权限轴（`space-write`/`capability-admin`），
   装配期 `ACTIVATION_IMPOSSIBLE`（D-26，`CONTRACTS.md` §16.2「轴值判据」段）；Kernel 对轴值只当不透明串；
   空白轴恒 `authorized:false` fail-closed。**投影侧**：只认机制见证、载荷自称不可信、按事件记录的
   `policyVersion` 查**冻结判据表**（v2 行只读历史语义，绝不按当前权限重解释历史）、查表 `lookupStandingRule`
   原型键/非函数 fail-closed（N6/N7，§16.2 包 4 纪律）。
5. 依赖本节的登记项：`G1-AUDIT-01`（审计计数持久化 = 一批新的机制域事件名，`READINESS.md:246`）、
   B.5-5（重定位事件名）、`G1-ROUTE-01`（随附审计判据从名单改谓词）。

### C.2 备选方案（新机制事件名的默认策略）

| 案 | 默认策略 | 谁签发 |
| --- | --- | --- |
| **C1 机制名命名空间默认预留**（G6-A 修法 (a)） | 机制域事件名封闭规则（前缀/命名空间规则，机制名全部落进封闭名单）；**新增机制名走冻结面流程**；通用通道写机制域名 ⇒ `EVENT_AUTHORITY_REQUIRED`（复用现码）；**领域事件名 = 所有权登记**：未登记名字通用通道不可写 | 机制名：用户裁定 + 冻结面流程；领域名：装配期 Capability 清单归属登记（机制核唯一性，双认领 ⇒ `AMBIGUOUS_AUTHORITY` 同码先例） |

### C.3 各自的不变量与代价

- **C1**：*不变量*——未登记/未预留名字的 mint 在机制上不可表达（deny-by-default）；机制自身写点走
  实现内部直写不经通用通道（五名预留先例，`CONTRACTS.md` §16.3①：「预留不误伤机制」）；每个事件名有
  唯一权威（与 `ownsKinds`/`ownsEventTypes` 同一本归属账，不建第二套）。*代价*——**存量未登记名**
  （`object-revised`/`record-backfilled`…）须处置：H 不可删改 ⇒ 历史行的名字改不掉，只能「旧名历史保留 +
  新写一律经预留/登记」或引入「判定读」的别名映射；所有合法写方（含运维工具、迁移器）承担登记成本；
  manifest 面加宽（现 `ownsEventTypes` 只登记「正式事件类型」，非正式域事件也占名 ⇒ 所有权账范围要裁）。
- **C2**：*不变量*——运行时零新增成本；防「名单与写点被一起改掉」的协同漂移。*代价/上限（必须写清）*——
  判据对象是**源码写点**，防不住插件通道与裸面 mint（G6B-D27-3 恰是运行时通道）；计算名/动态拼接识别不全；
  **单独采用等于维持 deny-by-exception**——C2 只能当护栏，不能当默认策略。
- **C3**：*代价*——两道判据都要维护、都要配变异锚点；*收益*——运行时 deny-by-default 补上设计缺口，
  构建面共生校验防 C1 的名单自身漂移（`REQUIRED_TRIGGERS`/SCHEMA 同源教训的镜像：名单与事实**必须异源**
  才有机验力）。

### C.4 建议与理由

**选 C3**，并冻结三条契约明句：

1. **默认策略**：机制名命名空间**默认预留**（deny-by-default）；新增机制事件名 = 用户裁定 + 冻结面流程，
   不由作者或席位自定；领域事件名由清单归属登记签发，未登记名字通用通道不可写。这条把「五名预留」
   从一次性修补转成规则的**第一个成员**。

### C.7 第六轮裁定补充约束（2026-10-31，本轮新增；只补不推翻）

裁定立场：「**C3 原则通过**」，并点名两条必须写入的约束——两条都是防「修一个洞造出
一族新洞」的反向护栏，冻结 C 节时与 C.4 三句同层：

1. **不得因正式事件名 deny-by-default 而破坏 Q37 的 Raw Intake 容错**：无法识别为任何
   正式事件类型的原始材料，仍须能以受控 Raw Intake 信封保存**原文与来源**
   （仓内落点：`CONTRACTS.md` §6 实测段「无法解析的原始材料仍可登记，保留来源；不产生对象」
   与「接纳失败只拒绝，绝不删除原始输入」；Q37 条文本体不在仓内，引证纪律同上）。
   deny 的对象是「冒充正式事件的**写入**」，不是「看不懂的材料进入库」——预留闸若把
   未识别类型连 Raw Intake 通道一起拒掉，就是把命名权威用成了存在性 oracle，
   违反本仓「拒写形态必须可归因、原始输入不得因机制判定而消失」的既有实测契约。
2. **`ledger.actor == authority_basis.actor` 只证明两字段一致，不证明授权真实存在**。
   可信性来自机制**内部统一的主体核验与授权取证入口**：`actor` 与信封必须**在同一授权
   上下文生成**（同一取证点、同一事务、同一已验证主体，C.4-2 的单点信封构造器是其机制
   落点）；**普通领域事件写入 Port 不得自行提供见证**（入参面无字段可填，§16.2 判据③
   先例的推广）。**构建期检查（C2）须以独立批准的事件注册契约核对写入点**——名单若与
   写入码同源，就永远自证一致：`REQUIRED_TRIGGERS` 与 SCHEMA 同源导致「删定义」成为
   digest 判据设计外真空，是同一族问题的已实测先例（G1-STORAGE-02，`RE-REVIEW-G6-A.md`
   §④ `:320-331`）。名单与事实**必须异源**才有机验力，这条同时约束 C2 的实现选型。
3. **历史事件名保留原样，新写入用新规则；不允许为统一命名重写既有 History Ledger**
   （C.5-1 两案共有的下限，本轮升级为冻结明句：H 面 append-only 不因命名整理开口子，
   「名字难看」与「名字违法」的处置都在读侧映射，不在写侧改写）。
