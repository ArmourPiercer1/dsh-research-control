### 11.2 作者自我失误（登记为纪律事件，不粉饰）

## 17. F-34 根因与修法：断言不该押在时序余量上

独立复审的 `attacks/review/r5-contention-repro.test.ts` 复现出同一个形态：父进程写**没有被拒**
（`expected undefined to be 'TX_CONTENTION'`）。它把结论定在"子进程持锁 2500ms"上，
而 `busy_timeout=2000ms` —— **余量只有 500ms**，负载下父进程稍晚开工就会在子进程提交后才重试。

这与我此前登记的 F-34 是同一个根因，只是我把余量从 3000ms 加到 8000ms 当过临时缓解：
**加大余量是把断言的正确性押在调度上，不是修根因。**

改法（`tests/helpers/hold-write-lock.mjs` + 用例）：子进程持锁直到父进程**断言完成后经 stdin
下发放行**；第三个参数退化为父进程崩溃时的安全阀，不参与任何时序假设。
于是断言窗口内锁必然持有——用例从 10.2s 降到 **2.05s**（那 2s 是 `busy_timeout` 本身的等待，
是机制行为，不是等待运气），全套并行跑 **绿**（此前时红时绿）。

两处必须写下的自伤与克制：

1. 我第一版把 `process.exit(0)` 删掉了，而 stdin 由父进程持有不会自己关，导致子进程永不退出、
   `close` 永不触发、用例挂死 30s。教训同 §14.3：**改同步结构要顺带检查退出路径**。
2. 我第一版把 stdin 的 `'end'` 也当作放行信号。这会让 `stdio[0]='ignore'` 的调用方
   （正是复审员那份 repro）在 fd0 立刻 EOF 时**当场提交**，把"等命令释放"退化成"立刻提交"，
   悄悄改掉别人文件的时序语义。现在只认显式 `release` 或安全阀到期，**定时语义保持原样**。

F-34 关闭：不是把红测试放宽，而是把"押在调度上的断言"换成"由同步驱动的断言"。
复审员 repro 自身的 500ms 余量属其文件所有，我只通报不改。

## 19. F-EV-R2 闭环：根因是**我自己的写侧漏盖戳**，不是读侧判据装错

第 11 轮回退时我留了个二选一：(a) 我的 ns→版本推导取错，(b) p2 那条测试确在读跨版本行。
按 §18 写的顺序先打值再动手，结论是**第三种**，两种都不是：

**凡是 revision≥2 的行，`contract_version` 都是默认空串**。

这解释了我上一轮看到的全部现象，而且比原判定更难看：

- 读侧一旦按"空标记 = 不可判定 = 拒绝"（R3-B，那条纪律是复审逼出来的）装上判据，
  **所有修订过的对象在快照面都不可读** ⇒ p2 那条测试被打断是**正确行为**，
  它无意间替我指出了写侧漏洞。
- 反过来，没装判据的面（快照、双时间）之所以"看起来没事"，正是因为它们对空标记睁一只眼——
  半门之所以能长期存在，是因为它掩盖了另一个更基本的缺陷。
- 也就是说：R3-B 我封的是"空串不被判据放过"，**却让自己的写侧持续生产空串行**。
  封了一条读侧后门，同时留了一条写侧前门。

修法三处（同一个判据函数，不搞第二套）：

1. **写侧**：`revise` 盖戳，取 `ns` 生效路由上的 `contractVersion`（装配后真实值，不是清单意图）。
2. **单对象读面**（`PluginFace.readLatest`、快照主读面 `readObject`/`readSnapshot`）：
   过 `assertContractVersion`，**拒读**。单对象面拒掉不损失任何东西。
3. **扫描面**（`readAsOf`）：过同一条判据，但失败形态是**剔除 + 计入回显 `hiddenByContractSkew`**。
   理由不是"让谁的测试变绿"，而是沿用**已被独立复验接受**的 F-24 先例：扫描面抛错会让
   一行旧形状毒化整页读取，而"整页为空"正是本项目最禁止被误读成"没有"的形态；
   剔除必须可归因，因此新增计数（与 `hiddenByInactiveCapability` 同族，只给数量不给 oid）。
   这条失败形态的选择是**设计裁量**，已单列待独立复验，不当成既定结论。

演化席位的两条红测试 `contract-version-skew.test.ts` T4a/T4b **转绿**（他们的文件未改一字）。

  `seq/space/event_type/actor/object_id/revision` …）；
- `Kernel.eventsFor`（`kernel.ts:407`）确实把 `select seq, payload_json from ledger …` 的
  `payload_json` **解析后原样返回**，并作为 `PluginFace.eventsOf` 交进插件面。

所以"版本判据没装在事件面"这句话在**代码层成立**。但我据此倾向的结论与直觉相反：

**这条可能是设计正确，而不是漏装判据。** 区别在读取的语义类型：

| 读面 | 语义 | 端出旧形状意味着 |
| --- | --- | --- |
| `readObject`/`readSnapshot`/`readLatest`/`readAsOf` | **当前状态**（"现在是什么样"） | 伪装成当前可读形状 ⇒ 静默错答，是缺陷（F-EV-R2） |
| `eventsOf`/`eventsFor` | **按记录时点的历史事实**（"当时记下了什么"） | 历史本来就该是当时的形状；给它套当前版本判据反而**篡改历史** |

ID-08/T-01/T-02 要求历史可按 `recorded_as_of` 回放，RPT 系列要求旧报告不被追改——
若事件面按当前路由版本拒绝旧事件，"升级即失忆"，那是更坏的失效。

因此待裁决的真问题不是"要不要装判据"，而是：**事件载荷是否需要携带写入时的契约版本，
以便调用方知道自己读的是哪个时代的形状**（可判定性），而不是**拒绝**它。
这与 F-EV-R2 的修法方向不同：那里是"拒读/剔除"，这里最多是"加一个可归因的标记"。

留待席位报告落地后合并裁决；在此之前不改 `src/`，也不把它登记为 P1（若最终判定是设计正确，
登记为缺陷就是反向污染审查记录）。

## 25. 对席位 `1faae161` 两条发现的处置（一驳一收，均经实测）

### 25.1 驳回：CTE 内 DML 这条**不是 P1**，该引擎上语法层就不存在

席位的怀疑是：`guardRead` 只锚定语句头部，`WITH x AS (DELETE … RETURNING) SELECT` 可绕过。
我用**内存库**探针（零写入，不碰 `.poc-data`，避免干扰正在跑攻击的席位）实测：

```
sqlite 3.53.4
ERR  cte-delete  near "delete": syntax error
ERR  cte-update  near "update":  syntax error
ERR  cte-insert  near "insert":  syntax error
```

SQLite 不像 PostgreSQL 允许数据修改语句出现在 CTE 体内。头部锚定确实是弱判据，
但**在这个引擎上它没有可绕的缺口**。定级不能建立在"其它数据库也许允许"上——
本 PoC 的存储契约就绑在 `node:sqlite` 3.53.4。

读句柄实际由**四道独立机制**合起来封死：头部锚定 + 多语句禁令（`/;\s*\S/`）+
`RawTx` 接口**只有 `run/all/get`、全 PoC 无 `exec`**（连多语句通道都不存在）+
引擎拒绝 CTE DML。任一条被拆，其余仍成立。

### 25.2 接受：触发器覆盖面比我说得窄（记 D-14）

席位说"三张追加表有触发器兜底，其余没有"——静态核对**成立**：
有触发器的是 `ledger`、`object_directory`（**仅 UPDATE，没有 no_delete**）、`check_report`、
`domain_state`、`ref_edge`、`records`；**没有**的是 `meta`（序列计数器）、`capability_version`（归属）、
`journal`、`projection_state`，而 `object_directory` 的 DELETE 是敞开的。
**我在文档里把"追加式存储"讲成了一条全局性质，实际它只是部分表的性质。**

但这条的正确归因不是"S-0 封了一半"：触发器只在**有写路径可达**时才重要，
而唯一的非受控写入口正是 D-7（`SqlitePort.raw` 无守卫 getter、`Kernel.port` 公开）。
所以两件事其实**是同一件事**——收口 D-7 会同时消掉这一整类；单加触发器则是给
一条已经封死的通道再上一道锁。**优先级：D-7 在前，D-14 是纵深防御。**

### 25.3 接受：`registeredEdges` 缺省让"可检测性"变成 opt-in（记 D-15，这条打在我设计上）

规则 `SYNTH_DUAL_SOURCE` 只在 `edges` 含 `USED_IN` 时触发，而装配根没交边视图时缺省是
`() => []`，此时双正源违规**静默通过且 coverage 仍报 COMPLETE**。
也就是说机制**分不清"没交边视图"和"交了的视图里没有这条边"**。

这正是我在读面上刚修过的那类错误——`empty-vs-absent`（F-24/S-2）——
**却只修了读面，没修校验输入面**。修法方向：边视图未交时 coverage 必须是 `INCOMPLETE`
（或独立的"未检"信号），不得报 COMPLETE。属合成领域，级别 **P2**。

## 28. D-7 已修：`Kernel.port` 不再公开，改为 symbol 内部通道（代价如实写）
