# 上层领域契约 Schema 基座：规范形态、编码与版本纪律

> **PR #47 · DRAFT-PROPOSAL · 2026-10-29。** 把[上层领域契约](H_S_R_DOMAIN_FOUNDATIONS_DRAFT.md)（PR #42，未合并）落到**可机器校验的编码层**：规定规范形态（canonical form）、字段编码、引用语法、时间/数量表示、注册表形态与版本纪律。本文件**不改变任何领域语义**；凡与 PR #42 契约层冲突，以契约层为准并应报错修正本文。
>
> **层级位置**：契约层（语义）→ **本层（编码与形态）** → 实现层（服务、存储、序列化后端）。本层只裁决"同一语义如何唯一地写成字节与键名"，不引入新的领域概念、新的对象类别、新的状态系统。
>
> **Proposed，不表示已实施、已冻结或已实证。** 本层的全部产物在实现前需要走冻结变更流程落地到 `schema/**`（见 §10），本轮**不写入 `schema/**`**。

## 2. 规范形态（HSR Canonical Form，下称 HCF）

| 编号 | 规则 |
| --- | --- |
| SF-01 | HCF 是**唯一规范性形态**：一个 JSON-compatible 值模型（对象/数组/字符串/布尔/null + 受限数值），持久记录、跨进程交换、摘要计算、导出前的中间态都以它为准。任何其它编码（列式、图三元组、W3C 投影、界面视图）都是**派生投影**，不得反过来成为真源。 |
| SF-02 | HCF 的键名**逐字采用契约层的领域阅读名**（`recorded_at`、`world_ref`、`registrant_ref`、`space_id`…），`snake_case`。理由：契约层的规则（`SL1-ENT-08`、`RL1-08` 等）以这些名字表述检查对象，同名单射使"规则 ↔ 槽位"可机验；任何改名都必须登记进[名称映射表](H_S_R_REGISTRY_SCHEMA_DRAFT.md)且只允许一一对应，禁止同义词并存的别名表。 |
| SF-02a | `@st` 与 `v`/`reason`/`ref` 是**值层保留键**，不占用槽位名，因此不与 SF-02 冲突：槽位名仍逐字等于契约阅读名，状态包裹只出现在值的位置。载荷槽位名以 `@` 开头即形态非法（保留前缀）。 |
| SF-02c | 契约各对象表以对象视角命名标识槽位（`entity_id`/`concept_id`/`association_id`/`argumentation_id`/`proposition_id`），本层持久形态统一为信封的 `object_id`（SS-09 禁止载荷重复信封键）。这**不是**改名冲突而是**同一槽位的两个视角**：阅读名 → 持久名的映射是本条，校验器只认 `object_id`；任何载荷里再出现 `<kind>_id` 即重复信封键，形态非法 |
| SF-02b | SF-02 的"逐字同名"只约束**持久形态的键**（信封与载荷）。接口**请求参数**、响应包络键、注册表条目键属于本层自身词汇：它们必须在本文档定义，但**不要求**在契约层存在同名条目；反过来，任何会落进持久形态的键都必须回到 SF-02 核对。凡本层命名的持久槽位（如 `frame_dimensions[]`）都必须在对象 Schema 表里显式标注"槽位名属本层命名" |
| SF-03 | HCF **不做紧凑假设**：缺键不等于任何状态。规范形态要求**槽位穷尽**——该 kind/子型注册表声明的每个槽位都必须出现，值是一个带存在状态标记的值（§3）。缺槽位 = 形态非法（`F-SCHEMA-INVALID`），**不得**解释为 `ABSENT`。 |
| SF-04 | 允许存在**稀疏写入形态**（调用方只提交它想声明的槽位），但它只存在于接口入口：服务在落规范形态前做**唯一一种**扩展——未提交的可空槽位一律展开为 `ABSENT`。扩展过程**不得**填任何值、单位、默认词表项或推断候选（UN-02、DF-08）。 |
| SF-05 | 每个 HCF 记录必须携带 `schema_version`（本层工件版本，整数）与 `space_id`（ID-02）。记录一旦写入，其字节与语义**永不改写**；新语义只能由新记录/新修订承载（ID-03、IC-01）。 |
| SF-06 | HCF 中不得出现持久化的"当前有效""最新版本""已确认"类字段（各契约的禁止字段清单）；此类语义只能由查询时的截点条件与投影得出（AX-03、DF-03）。 |

## 3. 存在状态的编码（五态）

契约层规定每个语义字段在任一修订中处于且仅处于一种状态（UN-01…UN-06）。编码固定为**带标签的值**（tagged value），标签键固定为 `@st`：

| 状态 | HCF 写法 | 说明 |
| --- | --- | --- |
| `DECLARED(v)` | `"world_ref": {"@st": "DECLARED", "v": <值>}` | `v` 必填且非空；`DECLARED` 允许 `v = null` **仅当**该槽位的类型本身允许 null 且契约如此声明（默认不允许） |
| `UNKNOWN(reason)` | `{"@st": "UNKNOWN", "reason": "NOT_YET_DETERMINED"}` | `reason` 必填，取值见契约层五态表；**禁止**携带 `v` |
| `NOT_APPLICABLE(reason)` | `{"@st": "NOT_APPLICABLE", "reason": "..."}` | `reason` 必填；禁止携带 `v` |
| `UNRESOLVED(ref)` | `{"@st": "UNRESOLVED", "ref": "<原样引用>"}` | 引用内容原样保留（UN-04）；禁止改写、清洗或"就近替换" |
| `ABSENT` | `{"@st": "ABSENT"}` | 由 §4 的扩展规则产生或登记者显式声明；不宣称任何信息状态 |

| 编号 | 规则 |
| --- | --- |
| SF-10 | `@st` 是保留键，不得作为业务键名。任何槽位的值若带 `@st`，其取值必须 ∈ 上述五值，否则形态非法。 |
| SF-11 | **空串、空数组、空对象、`false`、`0`、`null` 一律不是"未知"**（UN-01）。检查规则 `SL1-COM-03` 在本层的落点即：`v` 为空容器而 `@st = DECLARED` → `FAIL(STATE_UNDECLARED, VIOLATION)`。 |
| SF-12 | `UNKNOWN` 与 `ABSENT` 必须在编码层可区分且**可查询**（UN-03）：两者是不同 `@st`，且都进入 `declared_gaps[]` 的对应项（`declared_gap.state` 复用同一套标签）。 |
| SF-13 | **`WITHHELD` 不进入持久形态。** 它是读取时按调用者授权计算出的呈现状态（SP-02、UN-05）。落盘一个 `WITHHELD` 等于把"他空间存在某物"写进本空间记录，直接制造存在性侧信道（SP-07）。持久形态里只有 `DECLARED`/`UNKNOWN`/`NOT_APPLICABLE`/`UNRESOLVED`/`ABSENT`。 |
| SF-14 | 多值槽位：状态标记挂在**槽位**上；集合内每个元素可以是 `DECLARED` 或 `UNRESOLVED` 的带标签值，其余状态在元素位禁止（避免"集合里混着一个 UNKNOWN"被读成"整槽未知"）。集合为空且 `@st = DECLARED` → `FAIL`；未知集合一律 `@st = UNKNOWN(reason)`。 |
| SF-15 | 判定次序固定：**先**按空间/权限过滤算出呈现态，**再**报告记录态；被过滤者呈现为 `WITHHELD`（同空间确实缺失才可能呈现 `UNRESOLVED`），无法区分时保守取 `WITHHELD`（SP-02）。 |
| SF-16 | **`NOT_APPLICABLE` 不是"零义务"逃逸口。判据（先读这句）**：`NOT_APPLICABLE(reason)` 只有当该槽位所属规则条目声明了 `na_allowed: true`（`SCR-76`）**且** `reason` 属于同一条目声明的可接受理由集 `na_reasons[]` 时，才不产生 `FAIL`；未声明允许、理由越界、或理由是自由文本 → `FAIL(NOT_APPLICABLE_UNDECLARED, DEFICIENCY)`。唯一真源在规则条目里（`SCR-76`）；词表注册表**不得**再存一份槽位作用域，否则两处各自漂移，`SRG-21` 只管"码是否注册过"这一件事。**`na_allowed`/`na_reasons[]` 的来源**：它们是**契约许可的机器化形态，不是本层自创许可**——契约在对象表状列写的条件（如"非活动子型 → NA 带 reason"）是依据，规则条目须逐条编码。**双向一致性检查的契约侧输入是机器可读表，不是状列散文**：比对以契约必填性表逐槽位登记的 `可缺 / na_allowed / na_reasons` 为准（决策文档 §5.2 已登记该表为前置工件），条目声明了表里没有的豁免、或表里有豁免而条目缺席，都判一致性错误——散文条件没有可比对的结构，拿它当输入则"表里有豁免而条目缺席"这一向根本判不出来。**两个方向不要混**（此前同句既说"唯一真源在规则条目"又说"冲突时以契约为准"，像反向指定）：运行期评估的输入只有规则条目（校验器不解析契约散文）；修补方向以契约为准（不一致时改条目，不改契约散文）。理由：`NOT_APPLICABLE` 是唯一会**消掉必填义务**的状态，理由不受控则任何记录都能用一句"本例不适用"绕过 S-L1 检查，而这在形态上完全合法（`SF-11` 只拦空容器）。**`UNKNOWN` 的 `reason` 处置相反**：取自契约层五态表注册取值，但按 `OPEN` 词表对待（`SRG-21`），越界或未注册 → **记录照常保存** + `FAIL(VOCABULARY_CODE_UNREGISTERED, DEFICIENCY)`，**不得拒收**——否则"如实承认未知反而被系统拒绝登记"，与 `UN-06` 及接口层"绝不因如实声明 UNKNOWN 而降级"直接冲突。（本行此前把两段说明插在判据中间，主判句被切断约 200 词，且一处说明吞掉了句号；本轮按判据在前、说明在后重排。） |
| SF-17 | **带标签值的键集按状态封闭**（此前只散见于负面清单与测试清单，没有可校验的规则句）：`DECLARED → {@st, v}`、`UNKNOWN → {@st, reason}`、`NOT_APPLICABLE → {@st, reason}`、`UNRESOLVED → {@st, ref}`、`ABSENT → {@st}`；**出现集合外的键即形态非法**（写入被拒）。缺这条就能构造 `{"@st":"UNKNOWN","reason":"…","v":"HENT-7@r1"}` 这样的值——形态过关、而任何读 `v` 的消费方会从一个"未知"态里取走一个引用值，把未知当成已知。 |

## 4. 标识与引用编码

| 编号 | 规则 |
| --- | --- |
| SF-20 | `object_id`、`revision_id`、`record_id`、`report_id`、`vocabulary_code` 都是**不透明字符串**（长度上限 64 字符、大小写敏感、由登记方在创建时分配；上限是硬约束，实际长度可变，不存在「长度固定」这一承诺）。**禁止内容寻址身份**：不得由载荷内容哈希派生 ID。理由：内容相同即 ID 相同会**自动合并**同内容登记，直接违反 ID-07（合并永远是登记行为）与 RV-05（同指称冲突不自动合并）。摘要可以算，但不充当身份。 |
| SF-21 | `revision_id` 是对象内**单调递增序号**（`r1, r2, …`）的稳定编码，不得由内容摘要或时间戳充当；旧修订永不被改写或复用（ID-03）。 |
| SF-22 | 精确引用编码为字符串 `"${object_id}@${revision_id}"`，可带表示片段 `"@rev#<representation_id>"`。语法固定为 `^(HENT\|HCON\|HASS\|HARG\|HPRO)-[A-Za-z0-9_-]{1,58}@(r[0-9]{1,9})(#[A-Za-z0-9_-]{1,64})?$`，解析失败 → 形态非法。**注意**：该语法只保证形状，不保证与 V1 标识互斥——互斥由 SF-26 的封闭前缀注册表与 SF-27/SF-28 的槽位类型校验共同保证，不由语法自身保证。 |
| SF-23 | **逻辑引用（无版本）在 HCF 中不可表达**：正式槽位的引用类型只接受精确形式；"跟随当前"只允许出现在接口查询参数与界面导航参数中，且参数名必须显式为 `version_selection`（ID-05、RF-02、`SL1-COM-01`）。 |
| SF-24 | 非对象记录（H 记录、来源引用、检查报告、采用记录、快照）的引用使用独立前缀语法 `"rec:${record_id}"`，类型上**不能**赋给对象引用槽位（ID-08、RF-05）。需要"关于某条记录的论点"时改登记高阶 Proposition（RF-06），不得放宽槽位类型。 |
| SF-25 | `space_id` 不出现在引用字符串里；跨空间引用不存在（SP-05：复用只能靠导出/导入产生目标空间内的新对象）。任何形如 `space:obj@rev` 的写法都是形态非法。 |
| SF-26 | HSR `object_id` 的前缀是**封闭注册集** `{HENT-, HCON-, HASS-, HARG-, HPRO-}`（前缀只作命名隔离，不承载语义；增删前缀等价于注册面变更，须走冻结流程）。**V1 前缀注册表是冻结面**：`DOMAIN_SCHEMA.md` §1.1 明写「新增前缀必须 bump `.research/schema-version`」，`src/shared/ids/registry.ts` 是其机读镜像且注释禁止静默扩展，解析规则为**最长前缀优先**（`H` 与 `HENT` 存在包含关系）。因此本层的**临时裁决**（待契约层确认，见 DECISIONS A-10）：HSR 前缀**不进入** V1 那 25 项注册表；任何被提交的标识必须**逐条比对 V1 那 25 个锚定 pattern**（`schema/common.schema.json` `$defs/id*`，形如 `^H-[1-9][0-9]*$`），命中任一即拒。**不得用最长前缀匹配做这件事**：`src/shared/ids/registry.ts` 的 V1 集含前缀 `H`（`HISTORY_EVENT`，示例 `H-1001`），而 `parse.ts` 的 `longestPrefixMatch` 只做前缀包含判定，`HENT-…` 会命中 `H`——按前缀拒识会拒绝 100% 的合法 HSR 标识，与 SF-22 自相矛盾。锚定 pattern 无此问题（`HENT-1` 不匹配 `^H-[1-9][0-9]*$`）；被拒标识不交给 `src/shared/ids` 解析器，也不得落进 HSR 槽位。与 V1 的 25 个 ID pattern（`WS-`/`C-`/`F-`/`A-`/`REL-`…）**互斥**由「封闭前缀注册表 + 该校验」保证，不由字符串语法保证（SI-03、SD-12、A-10） |
| SF-27 | HSR `object_kind`（五值封闭）与 V1 `objectKind`（24 值，含 `CLAIM/FACT/ARTIFACT/RELATION`…）是**两个独立词表**：不共用注册表、不做隐式映射、不得互相填充；跨层联系只能显式登记（SI-03、DF-04） |
| SF-28 | **跨平面引用是唯一被许可的 HSR↔V1 连接形态**，且只能在 HSR 侧登记：记录可携带 `external_citations[] = {plane = V1, v1_kind, v1_id, citation_role ∈ {SOURCE_MATERIAL, RELATED_RECORD, SUPERSEDES_CLAIM, CONTEXT}, basis_refs[]: `(ref \| rec:)` 集合, basis_text: text}`。`v1_kind` 取值域 = V1 的 24 值 `objectKind` 封闭集（`schema/common.schema.json`），但它是**对本记录涉及何物的陈述**，不与 V1 注册表比对、不驱动任何 V1 解析；`v1_id` 必须匹配 V1 冻结 25 pattern 之一，且 `v1_kind` 与该 pattern 必须一致（`v1_kind=HISTORY_EVENT` 却给 `C-1@r1` → 形态非法）。**对应关系的落点是冻结面自身，本层不另立映射表**（新增表就成了第二真源）：kind 枚举在 `schema/common.schema.json` 的 `$defs/objectKind`，各 kind 的锚定 pattern 在同文件 `$defs/id<KindName>`（如 `idProject: ^PRJ-[1-9][0-9]*$`）；**两者之间没有显式映射表、只靠命名约定对应**，所以校验器必须由 `src/shared/ids/registry.ts` 的 `{prefix, kind}` 条目派生 kind→pattern，再与 `$defs/id<KindName>` 逐一比对，派生结果与 schema 不一致即冻结面漂移。**两侧基数不相等留下一个必须显式裁决的空档**（本轮核引用时实测发现）：`$defs/id<KindName>` 有 **25** 个 pattern，而 `objectKind` 只有 **24** 个值——`idManagementAction`（`^MA-[1-9][0-9]*$`）对应的 `MANAGEMENT_ACTION` 只存在于 `registry.ts`，不在 `objectKind` 枚举里。于是 `MA-*` 这类 id 是**pattern 合法但没有合法 `v1_kind` 可填**的：本层裁决为**不可跨平面引用**——携带 `MA-*` 的 `external_citations[]` 项按形态非法拒绝（不产生记录），而不是让实现者自行猜一个 kind 或放宽枚举。**两种失败必须分开**：pattern 不符 = **形态非法**（写入即 `TOOL_INPUT` 拒绝，不产生记录）；pattern 合法但所指 V1 对象不存在 = **不是错误**（断言语义，照常保存、不产生 finding），只有某条规则显式要求核验跨面指称时才由该规则产出 `F-UNRESOLVED`。命名用 `citation_role` 而非 `role`，以免与 SD-06 的"绑定承载角色"撞名。它是**断言**（「本记录涉及某个 V1 对象」），不是可解析的 `typedRef`：不参与身份判定、不得出现在端点/参与者/正式声明槽位、不隐含存在性校验（解析失败按未解析引用处理，走 `F-UNRESOLVED` 语义）。**禁止**把 V1 标识塞进 `external_identifiers[]` 等自由文本槽位当非正式连接通道——那会把身份文本变成隐式外键（EN-ID-1、`SL1-ENT-08` 同类风险）。V1 侧引用 HSR 标识需要新增事件字段，属冻结面变更，本层不做（SD-20、A-09） |

## 5. 时间编码

四类时间语义互不替换（T-01…T-05），编码上彼此为**不同槽位**，禁止互相填充：

| 槽位类别 | HCF 形态 | 规则 |
| --- | --- | --- |
| 瞬时（`recorded_at`、`adoption_at`、`checked_at`） | `{"@st":"DECLARED","v":{"epoch_ms":1761936855000,"display":{"iso":"2026-10-29T03:14:15+08:00","precision":"SECOND"}}}` | `epoch_ms` 与既有冻结 `$defs/epochMs`（`schema/common.schema.json`）同形，供排序与比较；`display.iso` 必须带**显式偏移**，禁止无偏移本地时间；`precision ∈ {SECOND, MINUTE, HOUR, DAY, MONTH, YEAR}` 表达**来源声明的精度**，禁止把低精度值补零伪装成高精度；两者换算后不在同一精度窗内 → 形态非法 |
| 声称时间 `claimed_time` | 同上，另有 `"kind": {"iso":…} \| {"interval":…} \| UNKNOWN` | 与 `recorded_at` 是两个槽位；混用即 `SL1-COM-06` FAIL |
| 描述区间 `described_interval` | `{"from": …, "to": …, "open_start": bool, "open_end": bool}` 或五态之一 | 开区间必须显式；缺省不等于全时域（契约层允许 `UNKNOWN`） |
| 采用范围 `adoption_scope` | 引用集合（稳定标识） | 采用时间与采用范围不可互相推导（AD-01…AD-04） |

| 编号 | 规则 |
| --- | --- |
| SF-30 | 时间值不得出现在标识符里，也不得参与身份判定（身份构成字段的比较只比 `@st` 与其引用集合，不比字节）。 |
| SF-31 | 查询侧的两个时间条件（`recorded_as_of` × `described_at`/`described_during`）是**请求参数**，不是记录字段；响应必须回显实际生效值与缺省（T-05、IC-H6）。编码见[接口基座](H_S_R_INTERFACE_FOUNDATIONS_DRAFT.md)。 |
| SF-32 | 摘要/导出等派生投影若只保留一个时间，必须显式标注丢弃了哪一类（AX-02、IC-P3 的 `lossReport`）。 |

## 6. 数量、单位与文本

| 编号 | 规则 |
| --- | --- |
| SF-40 | 数值一律以**十进制字符串**承载（`"v": "1.20"`），不用 JSON number 表达科学量值。理由：浮点会把 `1.20` 与 `1.2` 折叠为同一值，而测量精度属于命题的真值条件（PR-ID-4）。比较规则与等值判定不由本层裁决。 |

## 7. 摘要、规范序列化与等价

| 编号 | 规则 |
| --- | --- |
| SF-50 | **规范字节形态**（用于摘要与逐字节比较，如 XC-25 的"呈现视图必须同形"）：UTF-8；对象键按码位升序；无 insignificant 空白；字符串仅对控制字符转义；数组保持原序（顺序有语义：Assertion 链成员、路径步骤）；数值已是字符串故无歧义。 |
| SF-51 | 集合类槽位在规范字节形态下按其规范序列化**结果**排序（去序化），但记录内部保留登记序；两者区分必须可说明（哪些槽位是序敏感的集合由注册表声明）。 |
| SF-52 | `content_digest` 只对**资源载体字节**计算（A8 轴的 `HASH_MISMATCH` 判据），`record_digest` 只对记录的规范字节形态计算；两者都不是身份（SF-20），且都带算法标识（`{"alg": "...", "hex": "..."}`），算法切换产生新记录而非改写旧记录。 |
| SF-53 | **摘要相等 ≠ 语义等价**：本层不提供任何"内容相同即同一对象/同一命题/同一概念"的判定入口（NEV-01、ID-07）。 |

## 8. 版本与兼容纪律

| 编号 | 规则 |

## 11. 落地的最小验证预期（供后续测试设计，非已运行）

1. **形态正例**：五类对象各一个最小合法实例；一个"处处如实 `UNKNOWN`"实例仍达成 `S-L1`（`RPT-05`）。
2. **五态负例**：`{"@st":"DECLARED","v":[]}`、缺 `@st`、缺槽位被当作 `ABSENT`、`UNKNOWN` 携带 `v`、集合元素位放 `NOT_APPLICABLE`——各自必须被拒。
3. **引用语法负例**：无版本引用、`latest`、`space:obj@rev`、把 `rec:` 赋给对象槽位、ID 由内容哈希派生。
4. **摘要确定性**：同一记录的规范字节形态在两个实现上逐字节相同；`1.20` 与 `1.2` 不得折叠为相同摘要输入。
5. **视图同形**：同一猜测 ID 在"目标存在于他空间"与"目标不存在"两种世界下，呈现视图的规范字节形态必须**完全相同**（XC-25；编码要求见[检查 Schema](H_S_R_CHECK_SCHEMA_DRAFT.md)）。
6. **版本兼容**：新版本读取旧版本记录不产生字段注入；旧记录不因新必填槽位被回写（SF-62）。
7. **投影无损性**：导出往返对身份、来源、版本、未知项、状态轴无损，丢弃项逐条出现在 `lossReport`（IC-P3）。
