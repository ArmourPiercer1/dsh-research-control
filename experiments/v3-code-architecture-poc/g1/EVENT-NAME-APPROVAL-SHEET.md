## 0. 机制与格式（EA-2.4 步骤 2/3）

- **标记两处同现才算数**：① `contracts/event-registry/EVENT-CONTRACT-LEDGER.json` 的 `approved[]` 一条
  `{"approvedBy":"<非作者>","approvedOn":"<日期>","anchor":"<本文件路径或 PR 链接>"}`；
  ② 提交信息 trailer `Event-Name-Review: <日期> <批准人>`。
- **独立提交**：批准提交与实现代码**不同提交**，且**先于**实现该写面的 PR（EA-2.4 步骤 3）。
- **批准者 ≠ 实现者**（作者）。逐名办理，可按名分别指派，也可一名批准者签全部。
- **不批准的实际后果**（fail-closed，不是软失败）：未入账期间该名的写入口在装配期直接红
  （`ACTIVATION_IMPOSSIBLE`），消费该名的 PR 进入门禁即失败——这不是缺陷，是设计后果。

## 2. 批准者实际要做的三件事

1. **逐名判断命名纯度**：该名描述的是**机制运行事实**（机制自己产生、要进机制台账），还是把**领域语义**
   偷渡成机制名？（例：「命题被采纳」= 领域语义，不许；「原始材料已声明」= 机制事实，可。）
2. **看是否与已入账 7 名重复或重叠**：已入账 = `capability-enabled/-disabled/-transferred`、
   `object-registered`、`check-report-recorded`、`object-revised`、`record-backfilled`。
3. **签一行**：在 `approved[]` 写 `{approvedBy, approvedOn, anchor}` + 提交 trailer。其余由实现者处理。

**不需要**：读 PoC 代码、跑测试、判断事务时序、评估 S/H/R、决定 PR 顺序、审查（已冻结的）契约文本。

## 3. 时间成本与时机

- **单名 5–10 分钟**，五名一次过通常 **30 分钟以内**（材料即本表 + 各自条款一节）。
- **最晚时机**：PR-2 进入门禁前（PR-2 需要第 1、2 名）。**建议时机**：现在——PR-1（锚文件物化）落地后即可
  同批写入 `approved[]`；越晚越容易在 PR-2 门口卡住。
- 可以先只批 PR-2 的两名（第 1、2 项），PR-7/PR-10 的两名后补——**按名独立，不必打包**。

## 4. 谁能签

| 选项 | 是否合规 | 说明 |
| --- | --- | --- |
| 用户本人 | 合规（用户非实现者） | 最快；「独立性」来自角色分离而非外部机构 |
| 独立复核席（另一模型/座位，类似 R4/R5 的定向复核） | 合规 | 需要能读本表 + 三个条款小节；可一名席位签全部五名 |
| 人类同事 / 合作者 | 合规 | 最接近 EA-2.4 原意（「非作者评审者」） |
| 作者自己 | **不合规** | EA-2.4 明写「批准者 ≠ 实现者」 |
